# 2604.03962 — Predict, Don't React: Value-Based Safety Forecasting for LLM Streaming (StreamGuard)

Kavumba, Wataoka, Nguyen, Li, Ohagi (SB Intuitions), arXiv Apr 2026. Read in full (22 pp incl. appendices A–E).

## Research question
Text-based streaming guardrails (Qwen3Guard-Stream) treat streaming output moderation as *boundary detection*: find the first prefix that is already explicitly unsafe. Can we instead treat it as *forecasting*, i.e. predict expected harmfulness of likely future continuations from a prefix, supervised with Monte Carlo rollouts, so we don't need exact token-level boundary labels?

## Method
- Target is a value function: V*(x, y<=t) = E_{continuations ~ q(.|x,y<=t)} [O(x, y<=t || continuation)], where O is an offline safety judge scoring the *completed* response in [0,1].
- MC estimate: sample M continuations from prefix y<=t, judge each, take the mean -> soft target v_t in [0,1]. Terminal position uses the hard example-level label.
- Rollout distribution q = mixture of generators: Llama-3 8B and 70B, Qwen2.5 7B and 72B, 4 rollouts each (16 total) at temperature 0.7. Judge is Qwen3Guard-8B-strict (Gen).
- Rollouts are only needed for unsafe prompts; safe prompts get 0 targets.
- Model: full fine-tuned LLM backbone plus a linear head on the final hidden state of every token -> sigmoid risk score per prefix. Loss is BCE against the soft targets over the selected positions T(x,y).
- Supervision schedule: dense over the first D tokens, then stride S (e.g. "D64 S4" means every token for the first 64, then every 4th). The reference uses D64 S{1,2}. Budgeted, because long responses (WildGuardTrain) are expensive.
- Inference: threshold 0.5. *Debounced rule* (from Qwen3Guard-Stream): a response counts as unsafe after 2 consecutive unsafe predictions.
- Cross-tokenizer transfer: targets live in text-prefix space, so they can be reused on Gemma/Qwen backbones by pairing decoded text prefixes with targets.

## Models
Llama3 1B/3B/8B (main). Transfer models: Gemma3 0.3B/1B and Qwen3 0.6B/1.7B. Max sequence length 8192, global batch 128, LR 8e-6 (8B) or 1e-5, AdamW, StepLR gamma 0.85, up to 3 epochs, bf16, FSDP, 3 seeds. Checkpoints selected on Aegis2.0 val F1.

## Datasets
- Train: WildGuardTrain (allenai/wildguardmix, train split), Aegis2.0 (nvidia/Aegis-AI-Content-Safety-Dataset-2.0), ToxicChat (lmsys/toxic-chat), BeaverTails (PKU-Alignment/BeaverTails). Test splits follow WildGuard (Han et al. 2024).
- Input moderation eval: ToxicChat, OpenAI Moderation, Aegis, Aegis2.0, SimpleSafetyTests, HarmBench, WildGuardTest.
- Output moderation eval: HarmBench (responses), SafeRLHF, BeaverTails, XSTest-Resp, WildGuardTest, Aegis2.0.
- **Streaming timing eval: QwenGuardTest `response_loc` subset (813 unsafe responses), from the Qwen3Guard tech report (2510.14276). It gives sentence-level unsafe-onset spans, not exact token onsets.** The paper scores against the *end* of the annotated sentence, which in 91% of cases is the first sentence. HF: released with Qwen3Guard (likely `Qwen/Qwen3GuardTest`; verify).
- Overblocking: XSTest-Resp benign subset (FPR).

## Labeling of harm boundaries
- StreamGuard needs no boundaries: it uses soft MC future-risk targets for each prefix.
- Qwen3Guard-Stream (the baseline) uses boundaries: earlier prefixes are labeled safe, and the boundary and everything after it unsafe/controversial. The boundary comes from a rollout-and-judge pipeline and is tied to the tokenizer.
- Critique of "propagate final label to all prefixes" (Constitutional Classifiers style): generic scaffolds like "I"/"The" get labeled unsafe.

## Baselines
Qwen3Guard-Stream 0.6B/4B/8B strict/loose (main streaming baseline, official code commit 8a8b45a). Offline: LlamaGuard3/4, WildGuard-7B, ShieldGemma, NemoGuard, PolyGuard, Qwen3Guard-Gen.

## Metrics
- F1 for input and output moderation, with output scored under simulated token-by-token streaming plus debounce.
- **OnTime / Late / Miss**: let e_i be the last token of the annotated unsafe span. The first trigger is OnTime if <= e_i, Late if > e_i, and Miss if it never triggers. Comparisons across tokenizers align to Qwen prefix steps by incrementally decoding Qwen tokens to text, skipping invalid UTF-8.
- FPR on the XSTest-Resp benign subset.
- Latency: decision ratio rho = guardrail latency / generator per-token latency, and post-decision exposure L_extra = max(0, ceil(rho) - 1) tokens.

## Key numbers
- Input F1 avg: StreamGuard-8B 88.2 vs Qwen3Guard-Stream-8B-strict 86.7.
- Output F1 avg (streaming): 81.9 vs 80.4. Offline Qwen3Guard-8B-Gen-strict reaches 83.6, so the offline-to-streaming gap is about 1.7 F1.
- QwenGuardTest response_loc (8B): F1 97.5, OnTime 92.6%, Late 2.5%, Miss 4.9%, vs Qwen3Guard-Stream-8B-strict at 95.9 / 89.9 / 2.2 / 7.9. At 1B: 92.9% OnTime vs 88.3% (0.6B).
- XSTest-Resp: F1 89.9, FPR 4.5 vs 88.9 / 4.6.
- Transfer: Gemma3-StreamGuard-1B gets output F1 81.3, streaming F1 98.2, Miss 3.5%.
- Ablations:
  - Max-reduction is the most aggressive setting: OnTime 95.1%, Miss 3.8%, but output F1 drops to 79.0 and FPR rises to 6.8.
  - Min-reduction is conservative: OnTime 82.5%.
  - Single-model Llama-8B rollouts give OnTime 93.8%, while Qwen2.5-7B rollouts give only 85.9%, so the choice of rollout model matters a lot.
  - Supervision density barely matters (D1 S8 is about the same as D64 S1).
- Latency: guardrail decisions take 2.4–9.5 ms vs 9.8 ms/token for Llama3-8B generation, so rho < 1 for every pairing.

## Limitations
- The timing benchmark is coarse (sentence-level onsets), and in 91% of cases the onset is in the first sentence. **The lead time being measured is essentially within the first sentence, i.e. tens of tokens.** There is no tokens-ahead metric and no lead-distance analysis.
- Text-only. Activations of the generator are not used, and white-box Kelp/ShieldHead are not compared.
- Targets depend on the rollout pool and the judge (Qwen3Guard), so the setup is circular with the Qwen3Guard-defined policy.
- There is no calibration metric for the soft value (e.g. Brier score vs the true MC value).

## Relevance to observer/forecasting hypothesis
- **This is the closest prior to our "forecast, don't detect" framing.** But it is text-based and predicts a single scalar (expected final harm). There is no event-time / hazard distribution, no multi-scale latent summaries, and no comparison by lead distance. Our observer could be pitched as the white-box, hazard-valued, multi-horizon generalization.
- Label construction to copy: MC rollouts from the prefix, scored by a judge, averaged. For event-time labels, extend each rollout by judging prefixes of the continuation (e.g. sentence by sentence) to get the *first unsafe time* in each rollout. That yields an empirical distribution over time-to-unsafe, i.e. a discrete hazard target.
- Rollout settings (16 rollouts, T=0.7, mixed generators) and dense-then-strided supervision (D64 S4–S8 is sufficient) are cheap knobs to copy.
- Evaluation to copy: the OnTime/Late/Miss protocol on QwenGuardTest response_loc, the debounce rule, and XSTest-Resp FPR. Add AUROC-at-lead-k and "tokens before onset at first trigger".
- **Realism of 1024–2048-token leads:** in their main timing benchmark, the harm onset is in the first sentence 91% of the time. Single-turn harmful responses become unsafe early, so long leads are rare in standard safety data. Long-horizon evaluation would need constructed data: benign-preamble-then-harm, long-form responses where harm appears late, or multi-step/agentic transcripts.
- The baseline matches ours: a linear head on the same hidden state, trained on the same MC labels, is essentially the "direct probe" baseline.
